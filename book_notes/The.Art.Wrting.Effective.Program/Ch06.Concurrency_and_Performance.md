# Concurrency and Performance

**compare-and-swap** (**CAS**), or in C++ as `compare_exchange`. It takes two parameters: the first is the expected current value of the atomic variable, and the second is the desired new value. 

If the actual current value does not match the expected one, nothing happens; there is no change to the atomic variable. However, if the current value does match the expected one, the desired value is written into the atomic variable. 

The C++ `compare_exchange` operation returns *true* or *false* to indicate whether the write happened (*true* if it did). If the variable did not match the expected value, the actual value is returned in the first parameter. With `compare-and-swap`, atomic increment operation can be implemented in the following way:

```cpp
std::atomic<size_t> count;
… on the threads …
size_t c = count.load(std::memory_order_relaxed);
while (!count.compare_exchange_strong(c, c + 1,
  std::memory_order_relaxed, std::memory_order_relaxed)) {}
```

First, the actual name of the operation in C++ is `compare_exchange_strong`. There is also `compare_exchange_weak`; the difference is that the weak version can sometimes return `false` even when the current and expected values match (on x86, it makes no difference, but on some platforms, the weak version can result in a faster overall operation). 

Second, the operation takes not one but **two** memory order arguments: the second applies when the comparison **fails** (so it is the memory order for just the **load** part of the operation). The first applies when the comparison succeeds and the write happens.

How this implementation of the increment works? First, the current value of the **count**, `c` is atomically read. The incremented value is, of course, `c + 1`, but `count` cannot be assigned by this value because another thread could have incremented the `count` after the read but before the update. So a conditional write is needed: if the current value of the count is still `c`, replace it with the desired value `c + 1`. Otherwise, update `c` with the new current value (`compare_exchange_strong` does that) and try again. The loop exits only when the atomic variable did not change between the last time to read it and the time of being updated. This approach can be generalized to any computation: instead of `c + 1`.

Which version of `compare_exchange` should be used, and which memory order applies? On most CPUs, `compare_exchange` is a single atomic hardware instruction, and conceptually, the execution flow of `compare_exchange` looks like

```cpp
template <typename T> class atomic {
  mutex m;
  T value;
  bool compare_exchange_strong(T& old_v, T new_v) {
    std::lock_guard l(m);      // Get exclusive access
    T tmp = value;             // Current value of the atomic
    if (tmp != old_v) { old_v = tmp; return false; }
    value = new_v;
    return true;
  }
};
```

But this is not the most efficient way to implement `compare_exchange`. Generally, exclusive access to simply read the shared value is not needed. Of course, if another thread is writing the same value, the result of unlocked read can be wrong and needs to be verified under a lock, but only if the first read returns the expected current value and the compare-and-swap can proceed:

```cpp
template <typename T> class atomic {
  mutex m;
  T value;
  bool compare_exchange_weak(T& old_v, T new_v) {
    T tmp = value;           // Current value of the atomic
    if (tmp != old_v) { old_v = tmp; return false; }
    std::lock_guard l(m);    // Get exclusive access
    tmp = value;             // True current value of the atomic
    if (tmp != old_v) { old_v = tmp; return false; }
    value = new_v;
    return true;
  }
};
```

This is the classic `double-checked` locking pattern. It quickly return `false` in most cases when the current value does not match the expectation. However, there is a risk: it may return `false` based on a stale unlocked read, whereas the accurate comparison, done under a lock, would have returned `true` (and carried out the exchange).

Furthermore, some processor architectures, notably ARM, have the equivalent of a timed mutex, where the exclusive lock can fail if it takes too long to acquire. In this case, `compare_exchange_weak` also returns `false`, even if the atomic value is expected. Why yield the lock when it should proceed with the exchange? On CPUs with many cores, making everyone wait as long as it takes reduces the overall throughput; it is better to yield to another thread so it can get the lock faster and proceed with its computation.

Finally, why does `compare_exchange` take two memory order arguments? Take another look at the pseudocode: there are two separate operations on the atomic variable. Its value is always read at least once. That read operation may have a memory barrier. If the comparison leads to an exchange,  the operation may have a different memory barrier that is only engaged if `compare_exchange` succeeds. Hence, two memory order arguments: one for success and one for read-without-write.

Now add the compare-and-swap loop to the benchmark and compare it with the other two ways to increment a shared variable:

```cpp
// Example 01
// CAS increment
std::atomic<unsigned long> xa(0);
void BM_cas_weak(benchmark::State& state) {
  std::atomic<unsigned long>& x = xa;
  for (auto _ : state) {
    unsigned long xl = x.load(std::memory_order_relaxed);
    while (!x.compare_exchange_weak(xl, xl + 1,
            std::memory_order_relaxed,
            std::memory_order_relaxed)) {}
  }
  state.SetItemsProcessed(state.iterations());
}
```

## Lock-based, Lock-free, and Wait-free programs

In lock-based (with mutex) program, only one thread can hold the lock at any time, so that thread can increment the count without any further precautions. Once the lock is released, another thread can acquire it and increment the count. At any time, at most one thread can hold the lock and make progress; all remaining threads that need access are waiting on the lock. But even the thread that has the lock is not guaranteed to proceed: if it needs access to another shared variable before it can complete its job, it may be waiting on that lock, which is held by some other thread. 

In atomic based increment program, any thread that arrives at the atomic increment operation executes it without delay. Naturally, the hardware itself must serialize access to the shared data to ensure the atomicity of the operations (this is done by granting exclusive access to the entire cache line to one processor at a time). From the programmer's perspective, this exclusive access manifests as an increase in the time it takes to execute the atomic operation. However, in the code itself, there is no waiting for anything, no trying and retrying. This kind of program is called **wait-free**. In a wait-free program, all threads are making progress—that is, executing operations—at all times (although some operations may take longer if there is severe contention between threads for access to the same shared variable). A wait-free implementation is usually possible only for very simple operations (like incrementing a count), but whenever it is available, it is even simpler than the lock-based implementation.

In the `cas` based implementation, there are no locks; however, there is a loop that repeats an unknown number of times. In this regard, the implementation is similar to a lock: any thread waiting on a lock is also stuck in a similar loop, trying and failing to acquire the lock. However, there is one key difference: in a lock-based program, when a thread can acquire lock is not guranteed. In the program based on compare-and-swap, the only way a thread can fail to update the shared count is because some other thread updated it first. Therefore, of all threads trying to increment the count at the same time, at least one will always succeed. This kind of program is known as **lock-free**.

The above analysis shows three main types of concurrent programs:

- In a **wait-free** program, each thread is executing the operations it needs and is always making progress toward the final goal; there is no waiting for access.
- In a **lock-free** program, multiple threads may be trying to update the same shared value, but only one of them will succeed. The rest will have to discard the work they have already done based on the original value, read the updated value, and do the computation again. But at least one thread is always guaranteed to commit its work and not have to redo it; thus, the entire program is always making progress, although not necessarily at full speed.
- Finally, in a **lock-based** program, one thread is holding the lock that gives it access to the shared data. Just because it's holding the lock does not mean it is doing anything with this data, though. So, when concurrent access happens, at most one thread is making progress, but even that is not guaranteed.

## Different locks for different problems

Usually, standard `C++ mutex` on most platforms performs very poorly when it is used to guard access to a shared variable, especially when there are many threads trying to modify this variable at the same time. But is the lock inefficient because of its implementation, or is the problem inherent in the nature of the lock? Any lock is expected to be somewhat less efficient than the atomically incremented counter simply because a lock-based scheme uses two shared variables (the lock and the count) versus just one shared variable for an atomic counter. However, the mutexes provided by the operating system are usually not particularly efficient for locking very short operations .

The simplest and one of the most efficient locks for this situation is a basic **spinlock**. The idea of the spinlock is this: the lock itself is just a flag that can have two values, normally are `0` and `1`. If the value of the flag is `0`, the lock is **not locked**. Any thread that sees this value can set the flag to `1` and proceed. The entire operation to read the flag and set it to `1` has to be a **single atomic operation**. Any thread that sees the value of `1` must wait until the value changes back to `0` to indicate that the lock is available. Finally, when a thread that changed the flag from `0` to `1` is ready to release the lock, it changes the value back to `0`.

The simplest implementation of this lock looks like this:

```cpp
// Example 02
class BasicSpinlock {
  public:
  void lock() {
    while (flag_.exchange(1, std::memory_order_acquire)) {}
  }
  void unlock() {
    flag_.store(0, std::memory_order_release);
  }
  private:
  std::atomic<unsigned int> flag_ {};
};
```

The above implementation shows only the locking and unlocking functions; the class also needs declarations that make it **non-copyable**. 

Note that locking the flag does not use a conditional exchange, but always write 1 into the flag. The reason it works is that if the original value of the flag was `0`, the exchange operation sets it to `1` and returns `0` (and the loop ends). But if the original value was 1, it is replaced by 1 so it does not change at all.

Also, note the two memory barriers: locking is accompanied by the **acquire** barrier, while unlocking is done with the **release** barrier. Together, these barriers delimit the critical section and ensure that any code written between the calls to `lock()` and `unlock()` stays there.

However, the performance of this spinlock is terrible. To make it useful, it needs several optimizations.

First, note that if the value of the flag is `1`, the flag is left alone as it is. Why does it matter? The exchange is a `read-modify-write` operation; even if it changes the old value to the same value, it needs exclusive access to the cache line containing the flag. but exclusive access is not necessary to just read the flag.

This matters in the following scenario: a lock is locked, the thread that has the lock is not changing it (it is busy doing its work), but all other threads are checking the lock and waiting for the value to change to 0. If they do not try to write into the flag, the cache line does not need to bounce between different CPUs: they all have the same copy of the memory in their caches, and this copy is current, so there is no need to send any data anywhere. Only when one of the threads actually changes the value does the hardware need to send the new content of the memory to all CPUs.

Here is the optimization

```cpp
// Example 02
class LoadSpinlock {
  void lock() {
    while (flag_.load(std::memory_order_relaxed) ||
           flag_.exchange(1, std::memory_order_acquire)) {}
  }
}
```

The optimization here is that the flag is read until the value `0` is observed; then, the flag's values is swapped by `1`. The value could have changed to 1 between the time of check and the time when the exchange is called if another thread got the lock first. Also, note that when pre-checking the flag, the memory barrier doesn't matter since the final definitive check is always done using the exchange and its memory barrier.

Even with this optimization, the lock performs poorly. The reason has to do with the way operating systems tend to prioritize threads. In general, a thread that is doing heavy computing will get more CPU time on the assumption that it is doing something useful. Unfortunately, in this case, the most heavily computing thread is the one hammering on the flag while waiting for it to change. This can lead to an undesirable situation where one thread is trying to get the lock and has the CPU allocated to it, while another thread would like to release the lock but doesn't get scheduled for execution for some time. The solution is for the waiting thread to relinquish the CPU after several attempts so some other thread can run to finish its work and release the lock.

There are several ways for a thread to relinquish control of the CPU; most involve a system call. There isn't a universal best way to do so. The most common ways are the CPU pause instruction (emitted by inline assembly or compiler intrinsic), a call to `std::this_thread::yield()` (on Linux, this calls `sched_yield()`), or a call to sleep for a very short time (1 nanosecond) by calling `nanosleep()`. Note that while pause is a cheap hardware instruction, yield and sleep are system calls, which are expensive compared to hardware instructions. The best balance is achieved when trying to get the lock several times, then yield the CPU to another thread, then try again:

```cpp
// Example 02
class Spinlock {
  void lock() {
    for (int i=0; flag_.load(std::memory_order_relaxed) ||
      flag_.exchange(1, std::memory_order_acquire); ++i) {
      if (i == 8) {
        static const timespec ns = { 0, 1 }; // 1 ns
        nanosleep(&ns, nullptr);
        i = 0;
      }
    }
  }
}
```

The optimal number of attempts to acquire the lock before releasing the CPU will depend on the hardware and the number of threads, but generally, values between 8 and 16 work well. The best practice is to benchmark different implementations (pause, yield, sleep, or even a few pauses followed by a sleep) to see which one works best.

Here are the benchmark results:

![*Performance of a shared count increment: spinlock-based, lock-free (compare-and-swap, or CAS), and wait-free (atomic) on Sapphire Rapids CPU*](C:\book_notes\The.Art.Wrting.Effective.Program\images\B32053_6_6.png)

The spinlock has done very well: it is soundly outperforming the compare-and-swap implementation and gives the wait-free operation tough competition (the atomic increment is faster on one thread, where there is no contention, but slower otherwise).

Why does the spinlock perform so much better, specifically the lock with the `nanosleep` backoff? The reason is found in the low-level details of the cache coherency protocol.

When a thread acquires the lock, it does so by successfully writing 1 into the lock flag. To do this, the core must first obtain exclusive ownership of the cache line containing the flag. If other cores are holding it, it issues an invalidation request (often a Read-For-Ownership) to transition the line into the **Exclusive** (E) state. Once it holds the line exclusively, it performs the write, which transitions the line into the **Modified** (M) state.

When other cores try to acquire the lock, they first read the flag. This read request forces the owning core to write the dirty line back (or supply it directly) and downgrade its state from **Modified** to Shared (**S**).

This downgrade itself is relatively cheap. This is exactly why a Test-and-Test-and-Set (TTAS) lock reads first: if we instead used a naive atomic exchange on every iteration, every core would constantly demand the cache line be moved back to the **Exclusive** state just to get permission to write, even if all it does is replace a 1 with a 1.

However, the hidden cost of contention is accrued when the owning thread needs to unlock. Unlocking is a simple, unconditional write of 0. But to execute that write, the cache line must be upgraded from **Shared** back to **Exclusive**. The writing core must send an invalidation request to all other cores holding the line in **S**. In smaller CPUs, this is done via a simple broadcast, but this approach does not scale past 16 cores or so: full broadcast consumes massive bandwidth. In a server, dissipating the resulting heat is a major concern, and sustained full broadcasts to dozens of cores would literally melt the interconnect fabric.

Large x86 and ARM server chips use more complex network topologies (like ring buses or meshes) and snoop filters that track which core's caches hold specific lines to avoid chip-wide broadcasts and thus reduce bandwidth and power consumption. But nothing can circumvent the latency of waiting for acknowledgment (ACK) signals from all the cores that previously read the lock and currently hold the cache line in the **Shared** state.

The pause instruction does not help here. A paused thread puts its core into a short sleep (around 50 cycles), but the cache remains completely valid. The hardware still has to collect ACK signals from all paused cores, because a paused core still responds immediately to coherency probes—only its instruction execution is paused.

In contrast, `nanosleep` removes the thread from the OS scheduler entirely. The crucial factor is not what happens to the cache during the context switch, but the fact that the sleeping thread is no longer actively executing the spin loop. When the lock owner finally writes 0 and forces the cache line back to the Exclusive state, the sleeping threads are not awake to immediately re-read the flag and drag the line back to the Shared state. This aggressive backoff breaks the cycle. It drastically reduces the number of cores actively fighting for the cache line. At high contention, the invalidation broadcast and response traffic dominate execution time; reducing the number of cores actively participating in this sharing is the single optimization that matters above everything else.

These results and their understanding leave two questions: First, why don't all locks use spinlocks if they are so much faster? Second, why atomic operations are needed if the spinlock is so good?

The answer to the first question is different locks for different problems. The downside of the spinlock is that the waiting thread continuously uses the CPU, or is `busy waiting`. In contrast, a thread waiting on a system mutex is mostly idle (sleeping). Busy waiting is great if you need to wait for just a few cycles, such as the duration of an increment operation: it's much faster than putting the thread to sleep. However, if the locked computation consists of more than a handful of instructions, the threads waiting on the spinlock waste a lot of CPU time and deprive the other working threads of access to the hardware resources they need.

The second question introduce the difference between lock-based and lock-free.

## Lock-based versus Lock-Free, what is the real difference?

When the conversation turns to the advantages of lock-free programming, the first argument is usually `it is faster`. However, this is not necessarily true: lock implementations can be very efficient if optimized for a particular task. 

The issue of overhead on both lock-based and lock-free implementation are clear: spinning loops found in spinlocks and CAS-based lock-free programs can consume large amounts of CPU time while waiting. **If the expected wait is long and the contention is high, a lock may be more efficient**. However, if threads spend a lot of time waiting to complete a computation that can be done only on one thread at a time, the program is effectively serial at that point. A mutex will likely have less overhead than a CAS loop, but since there is no parallelism, the fastest option with zero overhead is simply to do the work on one thread. Naturally, this entire situation is to be avoided, but the solution usually involves finding an algorithm with more inherent parallelism.

Even **near-instant** access to shared variables puts significant stress on the CPU hardware, and this comes at a cost. So far, we have measured the throughput of the operation on a shared variable itself, but this is unlikely to be the main purpose of your program. (As we just pointed out, the best-case scenario for the performance of exclusive access is single-threaded speed, so if such access is all you do, you cannot benefit from threading.)

Most real programs access shared data in between independent parallel computations. We can construct a benchmark that emulates such a workload by interleaving shared data access with work that is local to each thread. For example, here is a benchmark that combines atomic shared increments with some independent computations:

```cpp
// Example 03
std::atomic<unsigned long> xa(0);
void BM_atomic(benchmark::State& state) {
  const size_t nshared = state.range(0);
  const size_t nwork = state.range(1);
  std::atomic<unsigned long>& x = xa;
  double y = 1;
  unsigned long n = 0;
  for (auto _ : state) {
    for (size_t i = 0; i != nshared; ++i) {
      benchmark::DoNotOptimize(x.fetch_add(1,
        std::memory_order_relaxed));
    }
    for (size_t i = 0; i != nwork; ++i) {
      benchmark::DoNotOptimize(y = sin(++n + cos(y)));
    }
  }
  state.SetItemsProcessed(n);
}
```

Note that when we count `items` of work, we only count the work done in parallel (the  
`sin`/`cos` calculations tracked by `n`). This mimics the common situation where data sharing is an implementation detail done `in service` of the computations that lead to the results we care about.

We can now compare the performance of different ways to provide exclusive access to the shared data. If the shared variable is guarded by a spinlock, we need to change the first loop to:

```cpp
// Example 03
unsigned long x = 0;
Spinlock S;
// … inside the benchmark loop …
    for (size_t i = 0; i != nshared; ++i) {
      std::lock_guard L(S);
      benchmark::DoNotOptimize(++x);
    }
```

We can similarly use a **mutex** instead of the *spinlock*. We then invoke this benchmark with different ratios of shared vs. independent workloads:

```cpp
// Example 03
static const long numcpu = sysconf(_SC_NPROCESSORS_CONF);
#define ARGS ->Threads(numcpu)->Args({1, 1}) \
  ->Args({1, 10})->Args({1, 100}) \
  ->Args({10, 1})->Args({100, 1}) \
  ->UseRealTime()
BENCHMARK(BM_atomic) ARGS;
BENCHMARK(BM_mutex) ARGS;
BENCHMARK(BM_spinlock) ARGS;
```

The outcomes depend on the processor and the number of threads. The following figure shows the results for the **Intel Sapphire Rapids** processor with 48 cores (96 threads) running one thread per *logical core*.

The most interesting result here is that, while the spinlock consistently provides better throughput for the shared access itself (the total number of increments of the shared variable per second), it is not always the best choice for the overall throughput of a program that uses shared data as needed to run large amounts of per-thread, independent computations. When **contention for the shared data is low**, atomic operations have lower overhead; the spinlock uses more CPU time, leaving fewer computing resources for the useful work (which in our benchmark is modeled by the independent workload computed by each thread). Only when the **contention is high** and **per-thread work is often interrupted to access the shared variable**,  the performance of the spinlock is better. The mutex remains much slower and less efficient across the board.

While this trend is universal, the **threshold** contention depends both on the hardware and on the specific instructions used to access the shared data. It is also worth asking whether the same trend (atomic operations have less overhead at low contention) holds if we lack a dedicated atomic instruction and must use a **CAS** loop. We don't need a complex example for this: something as simple as multiplication or computing the maximum value cannot be done atomically and requires a CAS loop. In this benchmark, to keep our results comparable, we will use CAS to implement the same increment:

```cpp
// Example 03
// ... inside the benchmark loop ...
    for (size_t i = 0; i != nshared; ++i) {
      unsigned long xl = x.load(std::memory_order_relaxed);
      while (!x.compare_exchange_strong(xl, xl + 1,
        std::memory_order_relaxed,
        std::memory_order_relaxed)) {}
      benchmark::DoNotOptimize(xl);
    }
```

As expected, the CAS loop perform worse than the atomic instruction. The question is: Will it outperform the spinlock at low contention?

![](C:\book_notes\The.Art.Wrting.Effective.Program\images\B32053_6_10.png)

From the above figure, CAS outperform the spinlock at low contention. 

This is a rather striking turnaround from the conventional wisdom derived from measurements obtained on hardware just a few years ago: **lock-free code can be more efficient, but its domain is that of low contention**. On the Sapphire Rapids CPU with 96 threads, the overhead of the lock (of any kind, spinlock or mutex) is significant even when the locked section is just *1%* of the total computation. On the 256-thread EPYC CPU, spinlock-based code is **slower** than lock-free code even when the locked section is *0.1%* of the total (only around *0.01%* does the locking become so `diluted` that its overhead is insignificant).

Amdahl's law can at least partially explain this: the cost of the critical section is essentially multiplied by the number of threads. But we already know that atomic operations are also executed one at a time; the only difference is that the hardware handles the exclusive access. The second reason is that the lock-free code is more predictable and, therefore, more pipeline-friendly. CPUs analyze the code dozens of instructions ahead, but they can't do it across the critical section boundary (or at least cannot do it as well).

This explanation can be confirmed by direct measurements using hardware performance counters. In particular, we want to measure the **core-bound stalls**, which tell us how often the execution unit is halted because it must wait for a core event to complete.

On Intel x86 CPUs, the performance counter `cycle_activity.stalls_total` measures the aggregate stalls. We can collect it, along with the generally useful cycle and instruction counts, using this `perf` command on Linux:

```
perf stat \
  -e cycles,instructions,cycle_activity.stalls_total \
  ./benchmark
```

For these tests, we want to run only one benchmark at a time: one contention ratio and one synchronization mechanism. We should also note that, at low contention, replacing `nanosleep` with a pause instruction (`_mm_pause()` on x86) yields slightly better throughput and much cleaner benchmark results, as it avoids profiling the system call overhead.

The results show that the execution unit is starved of work much more often when a spinlock is used, but it doesn't immediately tell us *why*. What it does explain is the observed performance difference, where the lock-based code runs at around **30%** of the speed of the lock-free code. It is not that the shared data updates take that much longer: at low contention, there are not enough of them to cause that much slowdown even if the lock takes several times longer than the atomic operation. The problem is that the lock somehow disrupts the execution pipeline for the perfectly independent, thread-local parallel code. In effect, spinlocks *poison* the execution unit, dragging down the performance of the surrounding code.

There are several suspects here:

1. **Branch Misprediction**: Both spinlock and CAS versions use loops and rely on the branch predictor. We expect the predictor to be highly accurate at low contention, but this needs confirmation.
2. **Store Buffer Stalls**: Store buffers hold the results of write operations locally in the core, allowing the CPU to execute subsequent instructions without waiting for data to move into the caches, coalescing results before flushing to memory. Atomic operations (including CAS) use the shared variable itself for synchronization. In comparison, a lock relies on an implicit execution dependency between at least two distinct variables: the lock flag and the data it guards.
3. **Instruction Reordering Limits**: We may suspect that the strict execution order required by the spinlock (acquire the lock → modify state → release the lock) restricts the CPU's ability to reorder instructions

Results shows spinlock has way more Store Buffer Stalls than atomic and CAS operation.

**lock-based** code uses multiple shared variables and must establish **happens-before** and **happens-after** relationships between operations on otherwise unrelated variables to maintain exclusive access guarantees. These relationships are enforced using memory barriers. Every time the lock is acquired (or a thread `wastes` an atomic exchange because it failed to acquire the lock), the memory barrier forces the Load-Store Unit to halt and wait for the Store Buffer to completely drain into the L1 cache. This is the only way the hardware can ensure x86 `near-TSO` (Total Store Order) semantics between two distinct memory addresses.

The atomic `fetch_add` and CAS avoid this entirely. Because they fuse the control and the data into a single hardware transaction on a single address, the CPU doesn't need to stall the Store Buffer to enforce a sequence between different locations. It just updates the L1 cache line and moves on, resulting in practically zero store buffer stalls (~12K vs 1.5 Billion). CAS also does not suffer from branch misprediction at very low contention (neither does the spinlock).

The **Reorder Buffer** (**ROB**) stall count, on the other hand, is counterintuitive. The test results show that the spinlock actually has fewer ROB stalls than the lock-free code.

This is because ROB stalls aren't always bad. In our lock-free code, the front-end of the pipeline is unconstrained. A *healthy* ROB stall occurs when the front-end decodes instructions faster than the execution units can process them, filling the ROB to capacity. The CPU is entirely compute-bound, feeding the math units as fast as physically possible. This is the best place to be: the performance of your code is limited purely by how fast instructions can execute, rather than artificial memory boundaries.

The ROB stalls in the spinlock-based code are fewer because the pipeline stalls on the memory barriers *before* it can fill the ROB. The front-end cannot reliably pump multiple iterations of math calcuation into the ROB because it is constantly slamming into the explicit memory fences of the spinlock's acquire/release cycle. The ROB never reaches its maximum capacity because the overall speed is artificially limited by memory synchronization, not by math calcuation throughput.

Overall, these results perfectly validate our hypothesis. The execution dependency required to guard a shared variable using a separate lock variable is fundamentally at odds with the execution model of modern wide-issue CPUs. On x86 CPUs, the explicit memory barriers required to synchronize the lock flag and the guarded shared value force the CPU to pessimistically serialize the pipeline, bleeding the performance of the non-shared code. **This memory fencing is the main source of the synchronization overhead, and it causes Store Buffer starvation**. This conclusion is applicable to any synchronization protocol that uses multiple unrelated shared variables and relies on memory fences to establish happens-before and happens-after relationships.

### Locks Problems

We now understand why, at low contention, locks perform significantly worse than lock-free code on modern CPUs. Conversely, the regime where we once expected lock-free code to be critically needed (the high contention for the shared data) is actually better handled on modern hardware by a well-designed spinlock. Note that some lock-free algorithms perform spectacularly well even on the latest CPUs; careful analysis shows that they do so by spreading contention across multiple shared variables so that the individual contention remains low.

However, there are other disadvantages that are inherent in the lock-based approach and do not depend on the implementation.

#### Deadlock

The first and most infamous danger is the possibility of the dreaded **deadlock**. A deadlock occurs when the program uses several locks: let us say `lock1` and `lock2`. Thread A holds `lock1` and needs to acquire `lock2`. Thread B already holds `lock2` and needs to acquire `lock1`. Neither thread can proceed, and both will wait forever because the only thread that can release the lock they need is itself blocked on a lock.

If both locks are acquired at the same time, the deadlock can be avoided if the locks are always acquired in the same order; **C++** has a utility function for this purpose, `std::lock()`. However, locks cannot be always acquired at the same time: when thread A acquired `lock1`, there was no way to know that it would need `lock2` as well, since that information itself was hidden in the data guarded by `lock1`.

#### Live Lock

If we cannot reliably acquire multiple locks, the solution would be to try to acquire them, then, if we fail to get them all, release the locks we already hold so the other thread can get them: In our example, thread A holds `lock1`; it would try to get `lock2` as well, but without blocking: most locks have a `try_lock()` call that either acquires the lock or returns `false`. In the latter case, thread A releases `lock1` and tries to lock them both again. This might work, especially in a simple test. But it has a danger of its own: the **livelock**, where two threads constantly pass locks to each other. Thread A has `lock1` but not `lock2`; thread B has `lock2`, gives it up, gets `lock1`, but now it can't get `lock2` back because thread A has it. There are algorithms for acquiring multiple locks that guarantee success eventually. Unfortunately, in practice, a long time may pass between *now* and *eventually*. These algorithms are also quite complex.

Note that there is a special case that is immune to the danger of deadlocks; this case is particularly important when we consider a spinlock or another fast lock as an alternative to atomic operations. If a lock guards a fragment of code that does not use other locks and does not execute any user-provided code, it is impossible to deadlock on it due to another thread holding some other lock. Such locks are sometimes called `embedded` or `captive` locks. Most spinlocks that are competing with atomics for performance fall into this category because hardware atomic operations support only native types. Without user-defined types, it is easy to ensure that the critical section cannot wait on another lock.

Even for captive locks, there is a danger, though the mechanism is different: if the thread currently holding the lock is somehow suspended, the entire program eventually stops as other threads hit that lock. If the OS scheduler suspends the thread, it will be resumed sooner or later (causing a temporary stall), but if the thread is blocked on I/O or simply crashes, the lock may be held forever.

#### Starvation

Even aside from the dangers of livelock and deadlock, lock-based programs suffer from other problems. One of the more frequent issues is **starvation** (often caused by **lock hogging**).

Suppose we have a computation protected by a lock. Thread A currently holds the lock and is working on the shared data, while other threads wait to do their part. However, the work is not a one-shot deal: each thread has many tasks to complete, and part of each task requires exclusive access to the shared data.

Thread A finishes one task, releases the lock, and then immediately moves to the next task, reaching the point where it needs the lock again. Although the lock was released, other waiting threads are still in the process of waking up (a slow OS operation), whereas Thread A is already `hot` on the CPU. Consequently, Thread A re-acquires the lock simply because the competition is not ready for it. Thread A's tasks rush through execution one after another, while nothing gets done on the other threads.

#### Convoying

There is also the opposite scenario: let's say we have mostly uncontended locking, where threads enter the critical section infrequently, so they rarely wait on each other. Then something happens, and one thread gets delayed in the critical section. The lock is held long enough that several other threads pile up waiting for it. Eventually, the lock gets released, and we should return to the old low-contention context... but we can't. There are enough threads waiting on the lock that, by the time they get through their critical sections, a few more threads are waiting.

This happens because contended locks have large overhead, so the same number of threads passing through the same critical section takes much longer once contention starts. And once it starts, it can never resolve itself until the rate of access to the shared data drops much lower than what the original, uncontended flow easily sustained. Critical sections of all threads now follow each other, bumper to bumper, like trucks in a convoy: the analogy that gave this problem its name, **convoying**.

#### Priority Inversion

Another problem with locks is that they do not respect any notion of priority: a low-priority thread that is currently holding the lock will block any high-priority thread that needs the same lock. The high-priority thread thus has to wait as long as the low-priority thread holds the lock: a situation that seems entirely inconsistent with the notion of high priority. For this reason, this scenario is sometimes called **priority inversion**.

### How Atomic And CAS Solve Lock Problems

First, in a lock-free program, threads are never blocked. In the worst-case scenario, where all threads attempt a compare-and-swap (CAS) operation simultaneously with the same expected current value, one of them is guaranteed to succeed (since the only way the value can change is via a successful CAS). The remaining threads will have to discard their computation results, reload the atomic variable, and repeat the computation, but the one thread that succeeded can move to the next task. This eliminates the possibility of a deadlock.

Without deadlocks (and the complex attempts to avoid them), we generally do not need to worry about livelocks either. Since all threads are busy computing their way toward the atomic operation, a high-priority thread is more likely to get there first and commit its results, while a low-priority thread is more likely to fail the CAS and have to redo its work. 

Similarly, while a single success does not theoretically position the `winning` thread for an advantage, in practice, it simply moves on. Whichever thread is ready to execute the CAS first is the one that succeeds. This naturally eliminates the convoy effect: no thread ever waits for a sleeper, though individual starvation is still possible if one thread consistently loses the race.

### Drawbacks of Lock-free Programming

The first is the flip side of its advantages: even the threads that fail their CAS attempts stay busy. This solves the priority inversion problem, but at a very high cost: in the case of high contention, a lot of CPU time is wasted doing work only to have it discarded and redone. Worse, these threads competing for access to the single atomic variable are consuming CPU resources that could otherwise be used by other threads performing unrelated computations. 

The second drawback is lock-free programs are incredibly difficult to design and implement correctly. The usual solution to the problem of complexity is modularization and encapsulation. 

# Building blocks for concurrent programming

The development of concurrent programs is quite difficult. The only hope of managing this complexity is to corral it into small, well-defined code sections or modules. As long as the interfaces and requirements are clear, the clients of these modules do not need to know whether the implementation is lock-free or lock-based. 

## The basics of concurrent data structures

Concurrent programs that use multiple threads need thread-safe data structures.But what is thread safety, and what makes a data structure thread-safe?

The highest level of thread safety is often called a **strong thread-safety guarantee**. It means the following: an object that provides this guarantee can be used concurrently by multiple threads without causing data races or other undefined behavior (in particular, all class invariants are preserved).

The next level is known as a **weak thread-safety guarantee**. It implies two things:

1. An object providing this guarantee can be accessed by multiple threads at once as long as all threads are limited to read-only access (calling `const` member functions of the class)
2. Any thread that has exclusive access to an object can perform any otherwise valid operation on it, regardless of what other threads are doing at the same time

An object that does not provide any such guarantee cannot be used in a multi-threaded program at all: even if the object itself is not shared, something inside its implementation is vulnerable to modification by other threads.

A class that provides a strong guarantee is sometimes simply called **thread-safe**.

If the class provides only a weak guarantee, it is called **thread-compatible**. Most STL containers offer this guarantee: if a container is local to one thread, you can use it in any otherwise valid way; however, if a container object is shared, you can only safely call `const` member functions (readers), or you must provide external synchronization for writers.

Finally, classes that do not offer any guarantees at all are called **thread-hostile** and, generally, cannot be used in a multi-threaded program at all.

## Lock-free programming with locks

Consider the case where we want to accumulate the *maximum value* from a sequence of numbers generated by many threads. The lock-based accumulator is trivial:

```cpp
// Example 06
unsigned long nmax {};                 // Shared state
Spinlock S;                            // Guards nmax
… on all threads …
unsigned long n = … new value …
{
  std::lock_guard L(S);
  if (n > nmax) nmax = n;
}
```

There is no atomic **max** instruction on mainstream CPUs, so the lock-free version uses a standard CAS loop:

```cpp
// Example 06
std::atomic<unsigned long> nmax {};     // Shared state
… on all threads …
unsigned long n = … new value …
{
  unsigned long cur = nmax.load(std::memory_order_relaxed);
  while (n > cur &&
    !nmax.compare_exchange_weak(cur, n,
     std::memory_order_relaxed,
     std::memory_order_relaxed)) {}
}
```

Here, we first check if the new value `n` is greater than the current value of `nmax` (`cur`). If it is, we attempt to update `nmax`. If another thread beats us to it (the CAS fails), we must try again, keeping in mind that the *new* value of `nmax` (reloaded into `cur` by the failed CAS) might now be greater than or equal to our `n`. If that happens, the loop terminates because our value is no longer a candidate for the maximum.

How do these two versions perform? Before we can measure, we have to decide on the data set. There are clearly two distinct limiting cases:

- Rare Updates: The new value almost never updates the current maximum (e.g., we hit the global maximum early)
- Frequent Updates: The new value frequently updates the current maximum (e.g., values grow monotonically over time)

![](C:\book_notes\The.Art.Wrting.Effective.Program\images\B32053_6_12.png)

After the benchmarks we saw earlier, it may come as a surprise that the spinlock-based implementation performs so poorly. After all, high-contention regimes usually favor spinlocks. But the chart provides a clue: spinlock performance is virtually identical regardless of the data pattern, whereas the CAS loop performs significantly better when updates are rare.

Let us look closely at our code again. The CAS loop begins with an atomic load: a read-only instruction that is much cheaper than the read-modify-write (RMW) instruction required by a CAS or a lock acquisition. If we do not need to update the maximum value (because our `n` is smaller than the current `nmax`), the CAS is never attempted. The program never writes to any shared variable; it only reads them.

Contrast this with the spinlock behavior: it begins with lock acquisition, which *always* modifies a shared variable (the lock flag must be changed from 0 to 1). This write occurs before we can safely read the shared maximum value. Remember that reading from a shared variable without exclusion is undefined behavior if another thread might be writing to it simultaneously.

It seems we have found a fundamental weakness of lock-based programming: if there is even a theoretical possibility that shared data could be modified, we are forced to acquire the lock (and incur the cost of a write) every time we read the data, even if modification never happens in practice.

There is a solution that does not require us to embrace the full complexity of lock-free programming. We simply need to borrow the key idea from our lock-free program: before we attempt an operation that *might* modify shared data, let us first verify if such a modification is *provably unnecessary*.

The solution employs the famous **Double-Checked Locking Pattern** (**DCLP**, also known in this context as the "Test-and-Test-and-Set" pattern):

```cpp
// Example 06
std::atomic<unsigned long> nmax_a {};     // Shared state
Spinlock S;                               // Guards nmax_a
… on all threads …
unsigned long n = … new value …
{
  if (n > nmax_a.load(std::memory_order_relaxed)) {
    std::lock_guard L(S);
    if (n > nmax_a.load(std::memory_order_relaxed))
      nmax_a.store(n, std::memory_order_relaxed);
  }
}
```

The first access to the shared data (outside the lock) exploits the atomicity of `std::atomic`. The write itself is indeed guarded by the lock, but that offers no protection to our first read because we have not acquired the lock yet. To avoid undefined behavior (a data race between a writer and a reader), the variable *must* be atomic.

If our local value `n` is not greater than `nmax_a`, there is nothing to do, so we skip the lock entirely. This is the key optimization that we learned from studying the lock-free program.

On the other hand, if it looks like this thread *might* need to update `nmax_a`, we must proceed with caution. Another thread could have bumped `nmax_a` even higher in the interval after we read it but before we acquired the lock. Our read-compare-write sequence is not atomic by itself. We make it atomic by acquiring the lock so that this sequence becomes the critical section.

Other threads can safely read `nmax_a` without the lock while our thread is in the critical section. However, no one else can *modify* it until we are done. 

Inside the critical section, we must check `nmax_a` a **second time** to ensure it is still less than our `n`. If it is, we proceed with the update. If not, we have wasted an expensive lock acquisition (a scenario similar to a failed CAS attempt) but correctness is preserved.

Now we can run the benchmark for lock-free vs. lock-based maximum accumulation again (DCLP is still strictly a lock-based approach).

The results show that, when updates are rare (the `rare updates` lines), there is absolutely no difference between the two implementations. This is expected: without updates to the shared maximum value, the two versions execute effectively identical instruction sequences: an atomic load followed by a comparison.

The DCLP version slightly outperforms the CAS loop for frequent updates. This is consistent with our earlier observation that a well-tuned spinlock is often faster than a CAS loop on modern processors under high contention. 

## Publishing protocol

A producer must finish creating data before consumers can safely read it. Locks ensure synchronization and memory visibility but add unnecessary overhead once the data becomes immutable. The goal is to guarantee that consumers see fully initialized data without requiring locks for subsequent reads.

The lock-free solution to this problem relies on a very specific protocol for passing information between the producer and consumer threads: 

The producer prepares data privately, then publishes it through a shared root pointer using an atomic release store. Consumers use atomic acquire loads to check the pointer, ensuring that those who observe a valid reference see fully initialized data. The data remains immutable after publication, allowing reads without locks. A publishing pointer class should encapsulate this protocol.

# Memory ownership in concurrent programs

A **publishing pointer** lets a producer safely share fully initialized data with consumers. Its `publish()` method uses an atomic release store, while `get()` uses an atomic acquire load to ensure readers see all writes made before publication.

The main challenge is **data lifetime**. Replacing a pointer does not mean the old data can be deleted immediately: readers may still be using it. A `republish()` method should therefore return the old pointer so the caller can arrange safe deletion. The reported benchmarks show little overhead for basic publication and access, though republishing is slower.

Key limitations:

- The pointer must be fully constructed before threads access it.

- Published data stays immutable; structural pointers may change through atomic operations.

- Multiple producers need additional coordination to prevent lost updates.

- Old data—and the publishing pointer itself—must remain alive until readers finish.

This design handles safe publication, but safe deletion requires a separate lifetime-management strategy, such as a thread-safe shared pointer.
