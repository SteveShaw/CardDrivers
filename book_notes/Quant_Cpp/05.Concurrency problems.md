### Spurious wakeups

A **spurious wakeup** occurs when a thread waiting on a condition variable returns from its wait even though no notification was sent.

Also, a real notification does not guarantee the condition is still true: another thread might consume the available work before the awakened thread reacquires the mutex.

Always check the condition under the mutex, using a predicate:

```
std::unique_lock<std::mutex> lock(m);
cv.wait(lock, [&] { return ready; });
```

This is equivalent to:

```
while (!ready)
    cv.wait(lock);
```

`wait` atomically releases the mutex and starts waiting, then reacquires the mutex before returning. The predicate form handles both spurious wakeups and conditions that are no longer true.

### What causes deadlock?

**Deadlock occurs when threads cannot proceed because each is waiting for something that cannot happen.**

A typical example is inconsistent lock ordering:

```
Thread 1: holds mutex A → waits for mutex B
Thread 2: holds mutex B → waits for mutex A
```

For resource deadlocks, four conditions hold simultaneously:

- **Mutual exclusion:** a resource has exclusive ownership.
- **Hold and wait:** a thread holds a resource while waiting for another.
- **No preemption:** resources cannot be forcibly taken away.
- **Circular wait:** a cycle of threads waits on resources held by the next thread.

Prevent lock cycles by using a consistent acquisition order, or acquire multiple mutexes together:

```
std::scoped_lock lock(mutexA, mutexB);
```

Other examples include locking the same nonrecursive mutex twice, or waiting for a worker to finish while holding a mutex that worker needs.

### What causes data races?

In C++, a **data race** occurs when:

- Two threads access the same memory location.
- At least one access modifies it.
- At least one access is non-atomic.
- Neither access *happens before* the other.

A data race causes **undefined behavior**. The accesses need not occur at precisely the same physical instant; the missing synchronization is what matters.

```
// Shared, non-atomic variable
int count = 0;

// Both threads execute:
++count; // Data race
```

Use a mutex or suitable atomic operations to coordinate accesses. As in your earlier example, release/acquire synchronization can safely publish non-atomic data.

A **race condition** is broader: a program’s correctness depends on timing. It can exist even when all accesses are atomic and there is no data race.

### Mutex versus spinlock

| Aspect                      | Mutex                                             | Spinlock                                   |
| --------------------------- | ------------------------------------------------- | ------------------------------------------ |
| While contended             | Can block the thread; may spin briefly first      | Repeatedly checks the lock                 |
| CPU use while waiting       | Low when blocked                                  | Consumes CPU execution time                |
| Waiting overhead            | Blocking and waking can involve scheduling        | Avoids blocking and waking                 |
| Best fit                    | General-purpose locking, potentially longer waits | Extremely short, bounded waits             |
| If the owner is descheduled | Waiters can sleep                                 | Waiters may waste CPU until the owner runs |

Both provide mutual exclusion and must establish appropriate memory ordering. Neither inherently guarantees fairness or prevents deadlock.

### When is a spinlock preferable?

A spinlock can be preferable when:

- The critical section is extremely short.
- The owner is likely running on another CPU core.
- Threads do not outnumber available execution resources.
- The critical section never blocks, performs I/O, or waits on another lock.
- Measurements show spinning is cheaper than blocking.

Spinlocks also appear in low-level contexts where sleeping is prohibited.

**For ordinary C++ application code, start with `std::mutex`.** If the owner is paused or descheduled, even a tiny critical section can produce a long spin.

### `std::scoped_lock` explains

`std::scoped_lock` avoids deadlock **when acquiring multiple mutexes together** by using a deadlock-avoidance algorithm equivalent to `std::lock`.

```
// Thread 1
std::scoped_lock lock(mutexA, mutexB);

// Thread 2 — reversed order is still safe
std::scoped_lock lock(mutexB, mutexA);
```

Naively locking one mutex and then blocking on another can produce:

```
Thread 1 holds A, waits for B
Thread 2 holds B, waits for A
```

Instead, a typical algorithm works roughly like this:

1. Lock one mutex.
2. Try to acquire the others without blocking.
3. If an attempt fails, release the mutexes acquired so far and retry.

Releasing the acquired mutexes breaks the `hold one while waiting indefinitely for another` cycle. **The standard guarantees deadlock avoidance for this acquisition; it does not prescribe this exact algorithm.**

`std::scoped_lock` also automatically unlocks all its mutexes when it leaves scope.

It does **not** prevent every deadlock. For example, separately acquiring locks can still deadlock:

```
// Thread 1
std::scoped_lock first(mutexA);
std::scoped_lock second(mutexB);

// Thread 2
std::scoped_lock first(mutexB);
std::scoped_lock second(mutexA);
```

The key is to pass **all the mutexes you need to acquire together into one `std::scoped_lock`**.
