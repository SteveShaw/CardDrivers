# Core C++ implementation problems

| Problem                              | What it tests                                 |
| ------------------------------------ | --------------------------------------------- |
| Implement `Vector<T>`                | RAII, allocation, move/copy, exception safety |
| Implement `UniquePtr<T>`             | ownership, move semantics                     |
| Implement `SharedPtr<T>`             | reference counting, atomics                   |
| Implement `String`                   | memory management                             |
| Implement simplified `std::function` | type erasure                                  |
| Implement `optional<T>`              | placement new, lifetime                       |
| Implement object pool                | allocation/performance                        |
| Implement memory arena               | alignment, pointer arithmetic                 |
| Implement LRU cache                  | hash table + linked list                      |
| Implement circular buffer            | indexing, memory layout                       |

A particularly realistic question is:

```cpp
template<typename T>
class Vector {
public:
    Vector();
    ~Vector();

    void push_back(const T&);
    void push_back(T&&);

    T& operator[](size_t);
    size_t size() const;

private:
    T* data_;
    size_t size_;
    size_t capacity_;
};
```

The interviewer can progressively ask about `realloc`, placement `new`, destructors, exception safety, move semantics, alignment, and cache behavior.

## Implement a simplified `std::vector`

Implement:

```cpp
template <typename T>
class Vector {
public:
    Vector();
    ~Vector();

    void push_back(const T&);
    void push_back(T&&);

    T& operator[](size_t);
    const T& operator[](size_t) const;

    size_t size() const;
    size_t capacity() const;

private:
    T* data_;
    size_t size_;
    size_t capacity_;
};
```

Requirements: dynamically grow the capacity and correctly construct/destruct `T`.

**Follow-ups:** Why can't you simply use `new T[capacity]`? How do placement `new` and `std::destroy_at` help? Implement copy/move constructors. What happens if a move/copy constructor throws during reallocation? How does `std::vector` decide whether to move or copy elements?

**Tests:** RAII, object lifetime, move semantics, exception safety, allocators.

## Implement `UniquePtr<T>`

Implement a simplified:

```cpp
template<typename T>
class UniquePtr {
public:
    explicit UniquePtr(T* p = nullptr);
    ~UniquePtr();

    UniquePtr(const UniquePtr&) = delete;
    UniquePtr& operator=(const UniquePtr&) = delete;

    UniquePtr(UniquePtr&&);
    UniquePtr& operator=(UniquePtr&&);

    T* get();
    T* release();
    void reset(T* p = nullptr);

    T& operator*();
    T* operator->();
};
```

**Follow-ups:** 

1. Why must copying be disabled? 

2. What happens during self-move assignment? 

3. How would you support custom deleters? 

4. How does `std::unique_ptr<T[]>` differ? 

5. Why can `unique_ptr` often have the same size as a raw pointer?

**Tests:** ownership, RAII, move semantics, templates.

## Implement simplified `SharedPtr<T>`

Implement reference-counted ownership:

```cpp
SharedPtr<Foo> a(new Foo);
SharedPtr<Foo> b = a;
```

Destroy `Foo` when the last `SharedPtr` disappears.

**Follow-ups:** 

1. Where should the reference count live? 

2. Why can't it simply be a member of each `SharedPtr`? 

3. Make the reference count thread-safe. Why doesn't an atomic reference count make the object itself thread-safe? 

4. How would `WeakPtr` work? Explain cyclic references. 

5. How does `make_shared` reduce allocations?

**Tests:** ownership models, atomics, control blocks, lifetime.

## Implement simplified `std::function`

Create something capable of:

```cpp
Function<int(int)> f =
    [](int x) { return x * 2; };

std::cout << f(10);
```

It should accept different callable types behind the same interface.

**Follow-ups:** 

1. How does type erasure work? 

2. How do you copy the underlying callable? 

3. How do you destroy it without knowing its concrete type? 

4. What is small-buffer optimization? 

5. How could you avoid heap allocation for small lambdas?

**Tests:** templates, type erasure, function pointers, object lifetime.

## Implement an LRU cache

Implement:

```cpp
class LRUCache {
public:
    explicit LRUCache(size_t capacity);

    int get(int key);
    void put(int key, int value);
};
```

Both operations should be average **O(1)**.

Example:

```textile
capacity = 3

put(1, 10)
put(2, 20)
put(3, 30)
get(1)
put(4, 40)
```

Key `2` should be evicted

**Follow-ups:** 

1. Why combine a hash table with a linked list? 

2. Why is `std::list` potentially undesirable in a low-latency system? 

3. Could you implement an intrusive list? 

4. How could you eliminate allocations after initialization?

**Tests:** hash tables, linked lists, complexity, cache behavior.

## Fixed-size object pool

You process millions of orders and want to avoid:

```cpp
new Order
delete order;
```

on the hot path.

Implement:

```cpp
template<typename T, size_t N>
class ObjectPool {
public:
    T* allocate();
    void deallocate(T*);
};
```

Memory should be allocated once.

**Follow-ups:** 

1. How do you store the free list? 

2. How do you handle alignment? 

3. How do placement `new` and explicit destruction work? 

4. Can the object itself contain the free-list pointer while unused? 

5. How would you make it thread-safe?

**Tests:** allocators, alignment, memory layout, performance.

## SPSC lock-free ring buffer

One market-data thread produces messages and one strategy thread consumes them.

Implement:

```cpp
template<typename T, size_t N>
class SPSCQueue {
public:
    bool push(const T&);
    bool pop(T&);
};
```

Constraints: no locks and no allocation after construction.

**Follow-ups:** 

1. Which variables need to be atomic? 

2. Explain acquire/release ordering. 

3. Why is `memory_order_seq_cst` unnecessary? 

4. What is false sharing? 

5. Why might you put producer and consumer indices on separate cache lines? 

6. What happens when the index wraps around?

**Tests:** atomics, memory model, cache lines, lock-free programming.

## Thread-safe blocking queue

Implement:

```cpp
template<typename T>
class BlockingQueue {
public:
    void push(T value);
    T pop();
};
```

`pop()` should block until an item exists.

Use:

```cpp
std::mutex
std::condition_variable
```

**Follow-ups:** 

1. Why must `condition_variable::wait()` use a predicate? 

2. What is a spurious wakeup? 

3. Should `notify_one()` happen while holding the mutex? 

4. How do you implement shutdown? 

5. What happens if multiple consumers exist?

**Tests:** mutexes, condition variables, concurrency correctness.
